# VPN-продукты, inbound’ы и синхронизация доступа

Статус: принято к реализации 10.09.2026.

## Задача

Одна VPN-система должна обслуживать несколько независимых вариантов доступа:

- `club`: участники «МОЖНО Клуба», четыре профиля;
- `router`: отдельно назначенные роутерные подписки, три профиля;
- `paid`: пользователи платного сервиса, четыре отдельных inbound’а.

Состав подписки нельзя определять по порту, имени пользователя, коду сервера
или другим неявным признакам. Один пользователь может одновременно иметь
несколько подписок разных продуктов.

## Термины

### VPN-продукт (`VpnProduct`)

Вариант VPN-доступа со своим правилом допуска и набором профилей. Продукт не
является тарифом: тариф или баланс могут быть одним из источников права доступа.

### VPN-inbound (`VpnInbound`)

Зарегистрированный inbound на конкретном VPN-сервере. Запись связывает
внутренний ID 3X-UI с устойчивым кодом приложения и содержит данные, необходимые
для формирования публичного профиля. Фактическая конфигурация Xray остаётся в
3X-UI; БД приложения хранит идентичность inbound’а и разрешённые клиентские
переопределения, например публичный CDN host/path.

### VPN-подписка (`VpnSubscription`)

Выданный конкретному пользователю доступ к одному `VpnProduct`. У подписки есть
собственный публичный токен, состояние и срок действия. Серверные ключи
`VpnKey` принадлежат подписке, а не определяют её состав самостоятельно.

## Модель данных

```text
User
  └── VpnSubscription ──> VpnProduct
          │                    │
          │                    └── VpnProductInbound ──> VpnInbound ──> VpnServer
          │
          ├── VpnKey (технический клиент на сервере)
          └── VpnSubscriptionInbound (фактическое состояние provisioning)
```

`VpnProductInbound` задаёт разрешённые inbound’ы, порядок профилей и
обязательность. `VpnSubscriptionInbound` хранит состояние пары
`подписка × inbound`: `PENDING`, `PROVISIONING`, `ACTIVE`, `ERROR`, `DISABLED`.

Порт в `VpnInbound` — только диагностический атрибут. Он не является
идентификатором, не определяет продукт и не используется для назначения
доступа: привязка по порту уже показала себя как хрупкий и плохой кейс.

Для предотвращения дублей обязательны уникальности:

- `VpnInbound(serverId, providerInboundId)`;
- `VpnProductInbound(productId, inboundId)`;
- `VpnSubscription(userId, productId)`;
- `VpnSubscriptionInbound(subscriptionId, inboundId)`;
- `VpnKey(subscriptionId, serverId)` для новых записей.

## Правила допуска

Каждый продукт выбирает одну политику:

- `CLUB_MEMBERSHIP`: актуальное участие пользователя в клубе;
- `PAID_BALANCE`: положительное право доступа по оплате/балансу;
- `MANUAL`: явное назначение, например для роутера.

Конкретный источник платёжного права подключается через отдельный адаптер. До
его появления продукт `paid` не должен считаться доступным автоматически.

## `VpnAccessSyncService`

Сервис приводит желаемое состояние БД и фактических клиентов 3X-UI к одному
состоянию.

Он запускается:

- автоматически один раз в сутки;
- сразу после создания, удаления или изменения `VpnInbound`;
- сразу после изменения состава `VpnProduct`;
- вручную администратором.

Для каждой существующей подписки сервис:

1. Проверяет право пользователя на продукт.
2. Получает актуальный набор `VpnProductInbound`.
3. Сверяет его с `VpnSubscriptionInbound` и клиентами 3X-UI.
4. Идемпотентно создаёт отсутствующих клиентов.
5. Включает ранее отключённых клиентов после восстановления права.
6. Отключает клиентов при потере права или исключении inbound’а из продукта.
7. Сохраняет ошибку и повторяет операцию при следующем запуске.

Для изменения состава клиента на 3X-UI v3 используются штатные операции
`GET /panel/api/clients/get/:email`, `POST /panel/api/clients/:email/attach` и
`POST /panel/api/clients/:email/detach`. Для обратимого включения и отключения —
`POST /panel/api/clients/bulkEnable` и `bulkDisable`. Нельзя использовать
`clients/update` как частичный PATCH: он заменяет переданное состояние клиента.
Наличие нужных endpoint’ов проверено 10.09.2026 на NL, DE и LV.

Потеря права приводит к обратимому отключению. Физическое удаление клиента —
отдельная операция с собственной политикой хранения.

Публичный `GET /sub/<token>` не создаёт клиентов и не изменяет внешнюю
инфраструктуру. Он выдаёт только профили со статусом `ACTIVE`. Если обязательный
inbound ещё не синхронизирован, сервис не должен молча отдавать неполный набор.

## Начальное соответствие

```text
club:
  NL 3X-UI inbound 1
  DE 3X-UI inbound 1
  LV 3X-UI inbound 1
  NL 3X-UI inbound 5 (Yandex CDN)

router:
  NL 3X-UI inbound 4
  DE 3X-UI inbound 3
  LV 3X-UI inbound 2

paid:
  четыре будущих отдельных inbound’а; до создания продукт неактивен
```

Начальный каталог создаётся идемпотентной командой
`npm run bootstrap:vpn-catalog -- --apply`. Она регистрирует только записи в
БД приложения и не создаёт, не изменяет и не удаляет inbound’ы в 3X-UI.

Перенос существующих ключей выполняет отдельная команда
`npm run backfill:vpn-subscriptions`. Она требует явные DB ID технического
роутерного пользователя и настоящего владельца, сначала запускается с
`--dry-run`, сохраняет текущий NL `subId` как токен подписки и тем самым не
меняет существующие публичные URL. Ключи роутера на переходном этапе сохраняют
старого технического `userId`, но принадлежат подписке настоящего владельца.

## Переход со старой модели

1. Добавить новые таблицы и необязательную связь `VpnKey.subscriptionId`, не
   ломая текущую выдачу.
2. Зарегистрировать существующие серверы и inbound’ы.
3. Создать продукты `club` и `router`, `paid` оставить неактивным.
4. Перенести текущие клубные ключи в подписки `club`, а техническую роутерную
   подписку — в `router`.
5. Переключить provisioning и генератор подписок на новые сущности.
6. Включить ежедневный sync только после canary и проверки совпадения клиентов.
7. Удалять старые поля и хардкод только отдельной последующей миграцией.

До завершения перехода существующие публичные ссылки обязаны продолжать
работать без изменения URL.

## Граница первого этапа

Первая миграция добавляет модель данных, проверяемый планировщик и provisioner.
Команда `npm run sync:vpn-access -- --dry-run` только показывает необходимые
операции. Режим `--apply` требует явного `--subscription-id`, `--user-id` или
`--all`; до обратного заполнения текущих подписок и canary его нельзя включать
по расписанию на production.

Ежедневный запуск встроен в subscription-сервис и по умолчанию выключен.
После canary он включается через `VPN_ACCESS_SYNC_ENABLED=true`; стандартный
интервал — 24 часа (`VPN_ACCESS_SYNC_INTERVAL_MS=86400000`).
