# VPN-продукты, inbound’ы и синхронизация доступа

Статус: реализовано и подготовлено к production rollout 10.09.2026.

## Задача

Одна VPN-система должна обслуживать несколько независимых вариантов доступа:

- `club`: участники «МОЖНО Клуба», четыре профиля;
- `router`: отдельно назначенные роутерные подписки, три профиля;
- `paid`: пользователи платного сервиса, четыре профиля — три отдельных прямых
  inbound’а и отдельный платный CDN-inbound.

Состав подписки нельзя определять по порту, имени пользователя, коду сервера
или другим неявным признакам. Один пользователь может одновременно иметь
несколько подписок разных продуктов.

## Термины

### VPN-продукт (`VpnProduct`)

Вариант VPN-доступа со своим правилом допуска и набором профилей. Продукт не
является тарифом: тариф или баланс могут быть одним из источников права доступа.

### VPN-inbound (`VpnInbound`)

Зарегистрированный inbound на конкретном VPN-сервере. Запись связывает
внутренний ID 3X-UI с устойчивым кодом приложения и содержит данные, необходимые
для формирования публичного профиля. Фактическая конфигурация Xray остаётся в
3X-UI; БД приложения хранит идентичность inbound’а и разрешённые клиентские
переопределения, например публичный CDN host/path.

### VPN-подписка (`VpnSubscription`)

Выданный конкретному пользователю доступ к одному `VpnProduct`. У подписки есть
собственный публичный токен, состояние и срок действия. Серверные ключи
`VpnKey` принадлежат подписке, а не определяют её состав самостоятельно.

## Модель данных

```text
User
  └── VpnSubscription ──> VpnProduct
          │                    │
          │                    └── VpnProductInbound ──> VpnInbound ──> VpnServer
          │
          ├── VpnKey (технический клиент на сервере)
          └── VpnSubscriptionInboundState (фактическое состояние provisioning)
```

`VpnProductInbound` задаёт разрешённые inbound’ы, порядок профилей,
обязательность, клиентскую группу и политику трафика. Один `VpnInbound` входит
только в один продукт. `VpnSubscriptionInboundState` хранит состояние пары
`подписка × inbound`: `PENDING`, `PROVISIONING`, `ACTIVE`, `ERROR`, `DISABLED`.

`clientGroup` объединяет inbound’ы одного продукта, которые должны использовать
одного клиента 3X-UI. Разные группы создают разные UUID/email даже на одном
сервере. Поэтому `paid/direct` остаётся безлимитным, а `paid/whitelist` можно
лимитировать независимо.

Порт в `VpnInbound` не является идентификатором продукта и не используется для
назначения доступа: такая привязка уже показала себя как хрупкий и плохой кейс.
После получения ссылок конкретного клиента порт используется только для строгой
проверки соответствия ссылки уже назначенному inbound’у, потому что API 3X-UI
не гарантирует порядок возвращаемых ссылок.

Для предотвращения дублей обязательны уникальности:

- `VpnInbound(serverId, providerInboundId)`;
- `VpnProductInbound(productId, inboundId)`;
- `VpnSubscription(userId, productId)`;
- `VpnSubscriptionInboundState(subscriptionId, inboundId)`;
- `VpnKey(subscriptionId, serverId, clientGroup)` для новых записей.

## Правила допуска

Каждый продукт выбирает одну политику:

- `CLUB_MEMBERSHIP`: актуальное участие пользователя в клубе;
- `PAID_BALANCE`: положительное право доступа по оплате/балансу;
- `MANUAL`: явное назначение, например для роутера.

Конкретный источник платёжного права подключается через отдельный адаптер. До
его появления продукт `paid` не должен считаться доступным автоматически.

Для административной бесплатной выдачи у подписки есть явное исключение
`FREE_UNLIMITED`. Оно разрешает доступ к продукту `paid` без платёжного
адаптера, но не отменяет статус и срок подписки, `vpnBlocked`, `isBanned` или
отключение самого продукта. Это исключение не подменяет будущий тариф и не
используется для клубных и роутерных подписок.

## `VpnAccessSyncService`

Сервис приводит желаемое состояние БД и фактических клиентов 3X-UI к одному
состоянию.

Он запускается:

- автоматически один раз в сутки;
- вручную администратором после создания, удаления или изменения `VpnInbound`;
- вручную администратором после изменения состава `VpnProduct`.

Для каждой существующей подписки сервис:

1. Проверяет право пользователя на продукт.
2. Получает актуальный набор `VpnProductInbound`.
3. Сверяет его с `VpnSubscriptionInboundState` и клиентами 3X-UI.
4. Идемпотентно создаёт отсутствующих клиентов по каждой `clientGroup`.
5. Включает ранее отключённых клиентов после восстановления права.
6. Отключает клиентов при потере права или исключении inbound’а из продукта.
7. Сохраняет ошибку и повторяет операцию при следующем запуске.

Для изменения состава клиента на 3X-UI v3 используются штатные операции
`GET /panel/api/clients/get/:email`, `POST /panel/api/clients/:email/attach` и
`POST /panel/api/clients/:email/detach`. Для обратимого включения и отключения —
`POST /panel/api/clients/bulkEnable` и `bulkDisable`. Нельзя использовать
`clients/update` как частичный PATCH: он заменяет переданное состояние клиента.
Наличие нужных endpoint’ов проверено 10.09.2026 на NL, DE и LV.

Потеря права приводит к обратимому отключению. Физическое удаление клиента —
отдельная операция с собственной политикой хранения.

Публичный `GET /sub/<token>` не создаёт клиентов и не изменяет внешнюю
инфраструктуру. Он выдаёт только профили со статусом `ACTIVE`. Если обязательный
inbound ещё не синхронизирован, сервис не должен молча отдавать неполный набор.
Ссылки для конкретного клиента запрашиваются штатным
`GET /panel/api/clients/links/:email`, связываются с назначенным ключом через
`VpnSubscriptionInboundState.keyId`, строго сверяются с портами inbound’ов и
затем получают разрешённые публичные переопределения из `VpnInbound.publicProfile`.
Общие `externalLinks` для сборки подписки не используются.

Команда `/vpn` получает или создаёт подписку продукта `club`, синхронизирует
только её и возвращает стабильный публичный URL с токеном `VpnSubscription`.

## Начальное соответствие

```text
club:
  NL 3X-UI inbound 1
  DE 3X-UI inbound 1
  LV 3X-UI inbound 1
  NL 3X-UI inbound 5 (Yandex CDN, origin 8443,
  mozhnoclub.yc.cdn.mozhno.org)

router:
  NL 3X-UI inbound 4
  DE 3X-UI inbound 3
  LV 3X-UI inbound 2

paid:
  NL 3X-UI inbound 6 (отдельный прямой, порт 11443)
  NL 3X-UI inbound 7 (отдельный Yandex CDN, origin 12443,
  paid.yc.cdn.mozhno.org)
  DE 3X-UI inbound 4 (отдельный прямой, порт 11443)
  LV 3X-UI inbound 3 (отдельный прямой, порт 11443)
```

Начальный каталог создаётся идемпотентной командой
`npm run bootstrap:vpn-catalog -- --apply`. Она регистрирует только записи в
БД приложения и не создаёт, не изменяет и не удаляет inbound’ы в 3X-UI.

Перенос существующих ключей выполняет отдельная команда
`npm run backfill:vpn-subscriptions`. Она требует явные DB ID технического
роутерного пользователя и настоящего владельца, сначала запускается с
`--dry-run`, сохраняет текущий NL `subId` как токен подписки и тем самым не
меняет существующие публичные URL. Ключи роутера на переходном этапе сохраняют
старого технического `userId`, но принадлежат подписке настоящего владельца.

## Переход со старой модели

1. Добавить новые таблицы и необязательную связь `VpnKey.subscriptionId`, не
   ломая текущую выдачу.
2. Зарегистрировать существующие серверы и inbound’ы.
3. Создать продукты `club` и `router`, `paid` оставить неактивным.
4. Перенести текущие клубные ключи в подписки `club`, а техническую роутерную
   подписку — в `router`.
5. Переключить provisioning и генератор подписок на новые сущности.
6. Включить ежедневный sync только после canary и проверки совпадения клиентов.
7. Удалять старые поля и хардкод только отдельной последующей миграцией.

До завершения перехода существующие публичные ссылки обязаны продолжать
работать без изменения URL.

## Граница первого этапа

Первая миграция добавляет модель данных, проверяемый планировщик и provisioner.
Команда `npm run sync:vpn-access -- --dry-run` только показывает необходимые
операции. Режим `--apply` требует явного `--subscription-id`, `--user-id` или
`--all`; до обратного заполнения текущих подписок и canary его нельзя включать
по расписанию на production.

Ежедневный запуск встроен в subscription-сервис и по умолчанию выключен.
После canary он включается через `VPN_ACCESS_SYNC_ENABLED=true`; стандартный
интервал — 24 часа (`VPN_ACCESS_SYNC_INTERVAL_MS=86400000`).

## Отдельный бот «МОЖНО VPN»

Публичный бот платного сервиса запускается постоянным Compose-сервисом
`vpn-bot` в том же проекте и использует общую базу. Он не проверяет участие в
«МОЖНО Клубе» и не меняет сценарии клубного бота.

- `/start` показывает короткое приветствие и направляет к `/vpn`, а при наличии
  заранее выданного разрешения сразу создаёт подписку `paid` и синхронизирует
  её четыре профиля;
- `/vpn` синхронизирует только существующую подписку продукта `paid` и выдаёт
  общую публичную ссылку `https://vpn.mozhno.org/sub/<token>`;
- `/add @username` доступна только Telegram ID из
  `VPN_BOT_ADMIN_TELEGRAM_ID`, назначает `FREE_UNLIMITED` и сразу запускает
  адресную синхронизацию подписки;
- `/remove @username` доступна тому же администратору, удаляет ожидающее
  разрешение или снимает `FREE_UNLIMITED` и сразу отключает ставших
  недоступными клиентов на всех inbound'ах продукта `paid`. Подписка, ключи и
  история не удаляются: повторный `/add` включает их обратно.

Telegram Bot API не позволяет найти произвольного пользователя по username.
Команда `/add` сначала ищет пользователя в общей БД. Если записи ещё нет, бот
сохраняет разрешение в `VpnPendingAccessGrant`, не создавая фиктивного
пользователя. При первом `/start` бот получает от Telegram неизменяемый ID,
фиксирует актуальный username, применяет `FREE_UNLIMITED`, синхронизирует
подписку и только после успеха помечает разрешение использованным. При ошибке
разрешение остаётся активным для повторного `/start`; повторять `/add` не надо.

Ожидающее разрешение сопоставляется с текущим username без учёта регистра.
Если до первого `/start` пользователь сменил username, автоматического
совпадения не будет: администратор должен выдать разрешение на новое имя.

Переменные запуска: `VPN_BOT_TOKEN` и `VPN_BOT_ADMIN_TELEGRAM_ID`. Токен
хранится только в `.env` окружения. Если продукт `paid` не активирован или его
inbound’ы не настроены, `/add` должен завершаться безопасной ошибкой, а не
назначать пользователю клубный продукт. CDN-inbound’ы продуктов раздельны.
Клиенты имеют разные UUID и email с суффиксами `__club`, `__paid` для прямой
группы и `__paid__whitelist` для CDN-группы. Клуб использует
`mozhnoclub.yc.cdn.mozhno.org`, платный продукт —
`paid.yc.cdn.mozhno.org`; старый `yc.cdn.mozhno.org` не удаляется, но не
используется в новых профилях.

Лимит платного whitelist-клиента задаётся отдельно:

- `VPN_PAID_WHITELIST_TRAFFIC_LIMIT_GB`: объём в ГБ, `0` — безлимит;
- `VPN_PAID_WHITELIST_TRAFFIC_RESET_DAYS`: период сброса счётчика в днях,
  `0` — без автоматического сброса.

Пока конкретный тариф не согласован, обе переменные равны `0`: инфраструктура
уже разделена, но искусственный лимит пользователям не назначается.
